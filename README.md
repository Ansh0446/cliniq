# ClinIQ

Pre-consultation clinical intelligence. Patients describe symptoms once; clinics receive a structured, patient-confirmed summary with a triage level.

**Phase 1 (patient dashboard) is built** on top of the base. Phase 2 (doctor and clinic portal) is next.

## Phase 1: patient flow

| Step | Route | What it does |
| --- | --- | --- |
| Dashboard | `/app` | Case list with status and urgency, live updates, profile nudge |
| Health profile | `/app/profile` | DOB, sex, blood group, emergency contact, allergies, conditions, medicines |
| Describe | `/app/intake/:caseId` (`new` to start) | Typed or dictated (Web Speech API) symptoms, autosaved draft, live red-flag scan, emergency modal |
| Review and confirm | `/app/cases/:id/review` | Edit the AI summary, rules re-check red flags on every edit, patient confirms |
| Choose clinic and send | `/app/cases/:id/send` | ClinIQ clinics (digital send, with consent) plus real nearby clinics from OpenStreetMap (call, directions, slip) |
| Case page | `/app/cases/:id` | Live timeline, summary, clinic info, activity trail, "more information requested" reply |
| Intake slip | `/app/cases/:id/slip` | Print-optimised page; "Save as PDF" in the browser print dialog |

**Nearby clinics.** The patient taps "Use my location"; the browser Geolocation API is used (no Google Maps API, no key). The exact position stays in the browser. The server receives coordinates rounded to about 1 km, queries OpenStreetMap's Overpass API (cached for 10 minutes, rate-limited per user), and returns clinics, doctors and hospitals. Clinics not registered on ClinIQ cannot receive cases, so they only get call, directions and the slip. Set `OVERPASS_URL` to use your own Overpass server; the public one is rate-limited and not for production traffic. The data source sits behind `findNearbyClinics`, so it can be swapped for Google Places later without touching the screens.

**Test clinic.** Migration 0005 adds one clinic named "ClinIQ Test Clinic (safe to delete)". It has no doctors, so cases sent to it are never read. Delete it before launch.

**Why the slip uses the browser print dialog.** PDF libraries cannot shape Indic scripts (for example Hindi) correctly. Browser printing renders any language the browser can display.

| Health profile | `/app/profile` | DOB, sex, blood group, emergency contact, allergies, conditions, medicines |
| Describe | `/app/intake/:id` (`new` to start) | Typing or Web Speech dictation, autosaved draft, live red-flag scan and emergency modal |
| Review | `/app/cases/:id/review` | Editable AI summary, urgency (read-only), re-scan after edits, confirm |
| Send | `/app/cases/:id/send` | ClinIQ clinics (digital send with consent) and real nearby clinics (OpenStreetMap) |
| Case | `/app/cases/:id` | Live timeline, activity, clinic details, reply to a "more information" request |
| Slip | `/app/cases/:id/slip` | Printable hand-over slip (print dialog, "Save as PDF") |

### Decisions worth knowing
- **Clinic search is hybrid.** Clinics registered on ClinIQ can receive cases digitally. Real clinics found near the patient come from OpenStreetMap (Overpass API) and are shown with call and directions links plus the slip, because nobody there can read a ClinIQ inbox.
- **Location uses the browser Geolocation API**, not Google Maps. The exact position stays in the browser; the server only receives it rounded to about 1 km, uses it for one query, and stores nothing. Overpass results are cached for 10 minutes. Set `OVERPASS_URL` to use your own instance.
- **One test clinic** ("ClinIQ Test Clinic (safe to delete)") exists so the digital send path can be tried. It has no doctors, so cases sent to it are never read. Delete it before launch (`delete from public.clinics where name like 'ClinIQ Test Clinic%'`).
- **The slip prints through the browser** instead of a PDF library. PDF libraries cannot shape Indic scripts such as Devanagari, so a Hindi description would come out broken. Browser printing handles every script. A QR code was left out because it has no clear use for clinics that are not on ClinIQ.
- **Voice is text only.** The Web Speech API returns text, not audio, so no recording is stored. Chrome and Edge support dictation; other browsers fall back to typing.
- **Emergency handling.** Deterministic rules scan while typing, again after the AI step, and again after edits in review. The modal cannot be dismissed without choosing, and the database refuses to confirm a case with red flags until the warning is acknowledged. Crisis lines in `src/components/emergency.tsx` are regional, so verify them for your deployment.
- **Rate limits.** `structureIntake` (8 per 10 min) and `findNearbyClinics` (12 per min) are limited per user in memory, per server instance.

### Not covered yet
- **Triage is advisory.** A patient's own session can write to their case row, so a determined patient could change the stored urgency or summary through the API. Doctors are protected by showing the most urgent of the stored, original-AI and confirmed values, the transcript and the patient's edits, and by the AI-output signature (see Final pass). A full fix would have the server write these fields itself with a service-role key.
- **Google Places** is not wired in; the clinic finder is isolated in `src/server/overpass.server.ts` if you want to swap the source.
- **Supabase Auth:** leaked-password protection is off (the advisor flags it). Enable it in Auth settings if your plan allows.

## Phase 2: doctor dashboard and clinic admin

| Screen | Route | What it does |
| --- | --- | --- |
| Inbox | `/doctor/inbox` | Red-flag cases pinned first, then urgency, then longest waiting. Filters: urgency, specialty, assignment (unassigned / mine / reviewed), clinic, search. Live updates. |
| Case | `/doctor/cases/:id` | Structured view, transcript with the patient's edits to the AI summary shown side by side, SOAP draft, private notes, pre-visit checklist, activity trail |
| Action bar | same | Start review, request more info, ready for consult, mark reviewed, assign, copy for EHR (two styles), export PDF / JSON / FHIR draft |
| Print | `/doctor/cases/:id/print` | Print-ready summary ("Save as PDF") |
| Clinic settings | `/clinic/settings` | Profile, map location, hours, specialties, intake settings, staff, licence checks, invites |
| Register a clinic | `/register-clinic` | Any signed-in user becomes admin of a new clinic |
| Join a clinic | `/join?token=...` | Doctor accepts an invite (must be signed in with the invited email) |

### Getting a working doctor inbox
1. Sign in and open `/register-clinic` to create a clinic. You become its admin.
2. In **Clinic settings**, choose **Add me as a doctor** (or invite a colleague and send them the link).
3. A platform operator must verify the clinic before patients can find it. Clinic admins cannot do this themselves. Make yourself an operator once in the Supabase SQL editor: `insert into public.platform_operators (user_id) values ('<your user id>');` then open `/operator` and press **Verify clinic**. (Without an operator account you can still run `update public.clinics set verified = true where id = '<clinic id>';` in the SQL editor.)
4. To test without a second account, patients can send to the seeded "ClinIQ Test Clinic" only if you add yourself to it: `insert into public.clinic_doctors (clinic_id, user_id) select id, '<your user id>' from public.clinics where name like 'ClinIQ Test Clinic%'; insert into public.user_roles (user_id, role) values ('<your user id>', 'doctor') on conflict do nothing;`

### Decisions worth knowing
- **Urgency is not taken on trust.** A patient can edit their own case row, so the inbox and case page show the most urgent of the stored value, the untouched AI assessment and the patient-confirmed summary, and any red flag forces "urgent". If the stored value was lowered, the case page says so. The inbox view also tolerates malformed JSON, so one bad row cannot break every doctor's inbox.
- **The SOAP note is a draft, not an AI note.** Subjective is built from the patient's report. Objective, Assessment and Plan are left blank for the doctor, and the Assessment line states the rule-based urgency is not a diagnosis.
- **Everything doctors change goes through checked database functions** (`doctor_set_case_status`, `doctor_mark_reviewed`, `doctor_assign_case`, `doctor_request_info`, `log_case_view`) which write the audit trail. "Ready for consult" from a freshly sent case first moves it to under review, because the status machine forbids skipping.
- **Opening a case is audited** (at most once per 30 minutes per browser session so patients do not see a long list of views).
- **Notes are private to the clinic's doctors.** Anyone can read colleagues' notes; only the author can edit or delete their own. SOAP drafts and checklists are per doctor.
- **No audio.** The spec's audio inspector is a transcript inspector, because Phase 1 stores text only. The page says whether the text was typed or dictated.
- **Invites are links, not emails.** ClinIQ has no mail sender. Copy the link and send it yourself. A link works for 14 days, once, and only for the invited email.
- **Clinics cannot verify themselves** and an admin cannot move a doctor membership to another user (database triggers).
- **FHIR is a draft.** The export is a FHIR R4 collection Bundle with free-text codes, patient-reported and "unconfirmed" statuses, and no diagnoses. It has not been run through a FHIR validator.
- **"Require triage sign-off" is stored only.** ClinIQ has no appointment booking yet, so the setting has no effect until scheduling exists.
- **Names.** Doctors see each other's names only through `clinic_staff`, so profiles stay private to their owners.

## Final pass

- **Operator screen (`/operator`).** Lists every clinic with its admin's name and email, doctor and case counts, and a Verify / Remove verification button. Only users listed in `platform_operators` can open it. The table has no API access at all; add operators from the SQL editor.
- **Signed AI output.** The server signs each AI result (HMAC-SHA256 over the case ID and the canonical JSON) and stores it in `cases.ai_signature`. When a doctor opens a case, the server re-checks it. If the stored AI assessment was edited, replaced or created outside the app, the case shows a warning and can never look more relaxed than "soon". Set `AI_SIGNING_SECRET` (32+ random characters) in production; without it a key is derived from `GEMINI_API_KEY`. This detects tampering after the fact; it does not stop a patient writing to their own row, and cases created before this migration show as unverified.
- **Account page (`/app/account`).** Patients can download everything ClinIQ holds about them as JSON, and delete their account. Deleting removes the profile and every case, including cases already sent to clinics. Clinic staff and operators cannot self-delete, because clinics and cases reference them. Whether you must keep clinical copies after a patient deletes their account depends on your jurisdiction, so check with counsel.
- **Timeline editing** is now available in the review step.
- **Deployment.** `npm run build` now produces a Node server in `.output/`, started with `npm start` (reads `PORT`, default 3000). A `Dockerfile` is included. I ran the built server locally and it served the pages; the Docker image itself has not been built here. Set the server-only variables from `.env.example` on your host, and pass the two `VITE_` values at build time because they are baked into the browser bundle.

## Patient assistant (chat)

A floating "Ask ClinIQ" button inside the patient area (`/app/*` only; doctors, clinic admins and the public pages never load it). It has two jobs and switches between them by itself:

- **Help:** explains how ClinIQ works, answering only from a fixed knowledge base (`src/lib/assistant/knowledge.ts`). Edit that file when the product changes.
- **Guided intake:** asks one short question at a time (main problem, when it started, how bad, trend, anything else), then shows the patient *their own words* in an editable box. "Build my summary" creates a normal draft and opens the Describe page with that text, so the existing red-flag rules, AI structuring, review and confirm steps all still apply. The assistant never writes the clinical summary itself.

Entry points: the floating button, plus "Ask the assistant" links on My cases, Describe, Review (urgency) and Choose a clinic.

### Safety design
1. **Emergencies are not left to the model.** Every message is checked with the same red-flag rules as the intake, in the browser (instant, works offline) and again on the server. A match shows the emergency warning and a fixed reply; the model is not called.
2. **A strict system prompt** (`src/lib/assistant/prompt.ts`): no diagnosis, no "could be", no medicines, doses, remedies or "wait / see a doctor" advice, no reassurance, messages treated as data not instructions, one question at a time.
3. **Replies are checked before they are shown** (`src/lib/assistant/guard.ts`). Patterns catch diagnoses ("you probably have..."), treatment advice and dosages; a match swaps the reply for a safe fixed message and drops any buttons or intake handoff. Quick replies and buttons are filtered too, and buttons can only go to four fixed pages.
4. **The intake transcript is checked for diagnoses**; if it fails, the patient's own messages are used instead. The patient edits it before anything is created.
5. **Privacy:** chats are held in the browser tab only and are not stored by ClinIQ; message text is never logged. The privacy policy and terms mention the assistant.
6. **Limits:** 24 messages per 10 minutes per user (in memory, per server instance), 1,000 characters per message, the last 14 turns and 8,000 characters sent to the model.

### Things to know
- Each message is one Gemini call, so it uses your Gemini quota. Chat replies use temperature 0.4.
- The pattern guard is a safety net, not proof. Test the prompts below on your real model and tighten `prompt.ts` / `guard.ts` if anything slips.
- The assistant can only see the patient's saved health profile (age, sex, allergies, medicines, conditions), never their cases.
- Doctors and clinic admins do not get an assistant. Adding one would need its own knowledge base and rules.

## Key decisions

- **Sending is the consent step.** Clinic staff can only read a case once its status is `sent` or later. Drafts and confirmed-but-unsent cases are invisible to every clinic.
- **Doctors never update cases directly.** They call `doctor_set_case_status`, `doctor_mark_reviewed`, `doctor_assign_case` and `log_case_view`, which check access and write the audit trail. A trigger enforces the status machine, so invalid jumps fail even with a leaked key.
- **Patients cannot read `case_notes`.** The table has clinician-only policies.
- **Rules beat the model.** Deterministic red-flag rules run in the browser and on the server. The merged triage takes the most urgent level, so the model cannot downgrade a rule match.
- **No diagnosis anywhere.** The extraction schema has no diagnosis, differential or treatment field, and the prompt forbids them.
- **Clinics self-register but start unverified.** `register_clinic` makes the caller an admin; patients only see clinics where `verified = true`. Set that flag yourself until you add a review step.
- **Doctors join by invite.** Admins insert into `clinic_invites`; the doctor signs in with the invited email and calls `accept_clinic_invite(token)`.

## Known gaps to close before real patients

- **Gemini model ID.** The spec names `google/gemini-3.8-flash`. That ID is unverified. `GEMINI_MODEL` defaults to `gemini-3.8-flash`; set the exact ID from Google AI Studio.
- **Red-flag rules are keyword-based** and English only. Have a clinician review and extend them, and test against real phrasing.
- **Rate limiting is in-memory** (per server instance) on `structureIntake` and nearby-clinic search. Use a shared store for production.
- **Triage is advisory.** A patient can technically edit their own case fields through the API, including urgency. Phase 2 should show doctors the original AI output and the red-flag rules result next to the patient-edited version.
- **Crisis lines** in `src/components/emergency.tsx` (Tele-MANAS 14416) and emergency numbers in `constants.ts` must be verified per deployment region.
- **Leaked-password protection** is off in Supabase Auth (an advisor warning). Turn it on in Auth settings if your plan allows.
- **Not yet browser-tested:** voice dictation, geolocation, Google sign-in, the Gemini call, and the live Overpass call were not run in the build environment.
- **Sent cases contain PHI.** Review your hosting region, backup, and retention setup against the regulations that apply to you (HIPAA, GDPR, India's DPDP Act).
- **Types.** `src/lib/database.types.ts` was generated from the live schema; regenerate it after any schema change.
